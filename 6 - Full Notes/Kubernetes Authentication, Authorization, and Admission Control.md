# Kubernetes Authentication, Authorization, and Admission Control
- To access and manage k8s resources or objects, we need to access specific API endpoint on the API server
- Each request goes through these stages
	- Authentication - Authenticate the user based on credentials
	- Authorization - Authorizes the request
	- Admission Control - Software modules that validate/modify the user requests

## Authentication
- Kubernetes does not have an *object* for user, nor does it store username
- Still it allow username for Authentication
- Normal User: 
	- Managed outside of k8s cluster via independent service
	- Common examples:
		- Client certificates (`kubectl` with certs)
		- Static username/password files (rare, not recommended)
		- Cloud provider IAM (Google, AWS, Azure)
		- OIDC providers (Keycloak, Auth0, etc.)
- Service Accounts: 
	- Allow in-cluster process to communicate with the API server. 
	- Most service accounts are created automatically via API server, but can also manually. 
	- Service account tie to namespace and mount the respective credentials.
- K8s also support anonymous requests, and user impersonation.

## Authorization
- The API requests attributes are reviewed by k8s include user, group, resources, etc
- These are evaluated against policies to know whether to accept or deny the request
- Authorization mode in k8s include: Node, Attribute-based access control (ABAC), role-based access control (RBAC), and Webhook (third-party services)

### Create Key and CSR with OpenSSL
To create a user, we create a private key and CSR (Certificate Signing Request)
- CSR is a proof that you hold the private key and is a request for CA to sign your certificate
- Here CN is the username, and O is the user group
```bash
-- Create the key
openssl genrsa -out bob.key 2048

-- Create the CSR
openssl req -new -key bob.key \
  -out bob.csr -subj "/CN=bob/O=learner"
```

### Create CSR object in K8s
We first define a YAML manifest for the CSR
```yaml
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: bob-csr
spec:
  groups:
  - system:authenticated
  request: <base64-encoded CSR>
  signerName: kubernetes.io/kube-apiserver-client
  usages:
  - digital signature
  - key encipherment
  - client auth
```
We convert the CSR generated by OpenSSL to base64 and paste into the request field
```
cat bob.csr | base64 | tr -d '\n','%'
```
Submit and approve CSR
```
kubectl create -f signing-request.yaml
kubectl get csr

kubectl certificate approve bob-csr
kubectl get csr
```

### Using the Certificate
We first obtain and decode the signed cert
```
kubectl get csr bob-csr \
  -o jsonpath='{.status.certificate}' | \
  base64 -d > bob.crt
```
Create a user with kubectl
User = cert + key
```
kubectl config set-credentials bob \
  --client-certificate=bob.crt \
  --client-key=bob.key
```
Create a context
Context = cluster + namespace + user
```
kubectl config set-context bob-context \
  --cluster=minikube \
  --namespace=lfs158 \
  --user=bob
```

### Create Role
Define manifest
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: lfs158
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "watch", "list"]

```
Create object
```
kubectl create -f role.yaml
kubectl -n lfs158 get roles
```


### Create Role Binding
Create manifest
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-read-access
  namespace: lfs158
subjects:
- kind: User
  name: bob
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

```
Create object
```
kubectl create -f rolebinding.yaml
kubectl -n lfs158 get rolebindings
```

## Absence of User Object
Kubernetes **does not have a User object**. A “user” in Kubernetes is **not stored, created, or managed** by the cluster.

Instead, a user is an **identity string produced during authentication** (e.g. from a client certificate, OIDC token, or cloud IAM). For example, when a request is authenticated with a certificate containing `CN=bob`, the API server temporarily treats the request as coming from user `bob` (and associated groups).

Key points:
- **Users are ephemeral**: they exist only while a request is being evaluated.
- **RBAC matches strings**, not objects: `kind: User` in a RoleBinding means “match this username,” not “reference a stored resource.”
- **kubectl does not define users**: it only sends credentials; the API server determines the username.
- **kubeconfig `users:` are client-side aliases**, mapping names to credentials, not Kubernetes users.
- **ServiceAccounts are different**: they *are* real Kubernetes objects with lifecycle and storage.

In short: **Authentication provides a username; RBAC authorizes that username. No User object is ever created.**

## Admission Control: The Final Policy Gate
Admission Control is the **third and final stage** of Kubernetes API request handling, executed **after Authentication and Authorization**. Its role is to **enforce cluster-wide policies** and optionally **modify requests** before they are persisted.

Key characteristics:
- Runs **after RBAC allows** a request
- Enforces **policy**, not identity or permission
- Applies to **all API objects**

Admission controllers are of two types:
- **Mutating**: modify requests (run first)
- **Validating**: accept or reject requests (run after mutation)

Common admission controllers:
- `ResourceQuota` – enforce quota limits
- `LimitRanger` – apply default resource limits
- `PodSecurity` – enforce pod security standards
- `DefaultStorageClass` – inject storage defaults
- `AlwaysPullImages` – enforce image pull behavior

Admission controllers are enabled on the API server using:
`--enable-admission-plugins=<ordered list>`
