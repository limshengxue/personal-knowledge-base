# 3.1 Data Models and Query Languages
## Declarative Query Languages
- Specify what we want but not *how* to achieve the goal
- This give opportunity to the query optimizer to decide which indexes and join algorithms to use and in which order to execute the parts of the query

## Relational vs Document Model
### Relational Model
- Originate from a theoretical proposal
	- Data organized into *relations* (tables) where each relation is an unordered collection of *tuples* (row)
- Earlier competitors are *network model* and *hierarchical model* but never worked out
- Document model came out as a strong alternatives in the NoSQL trend

### The Object-Relational Mismatch
- Awkward translation layer between *object* and the *relational tables* in application code and database
- Sometimes called *impedance mismatch*

#### ORM (Object-relational mapping)
- Framework to reduce boilerplate code of this translation layer
- Some common problems
	- Complex and can't completely hide the difference
	- Generally for OLTP only
	- ORM mainly supports OLTP relational database only
	- ORM does not guarantee efficient when it direct generate the schema/query

#### One-to-Many Relationships
- Document model is often a more close representation of a 1-to-many relationships
- It also provide better *locality* than a multi-table schema when searching by eliminate joins

### Normalization, Denormalization and Joins
- Whether to store an ID or a text string for a fields (e.g. country of a user) is a *normalization* question
- Using ID allow the data to be more normalized
- Advantage of normalization is to reduce duplication (we store ID as reference to 1 master record), this allow easier updates in the future with lower risk of inconsistency and high efficiency
- The trade-offs is an additional lookup to translate the ID into human-readable field which is accomplish using *join* in relational database
- In short, normalized data is *faster to write, slower to query* and denormalized data *vice versa*
- Denormalized data can also be viewed as a form of *derived data* [[1.2 - Trade Off In Data Systems Architecture#Derived data systems]]
- Document databases usually use denormalized data due to lack of *join* support
- Normalization tends to be better for *OLTP* for fast update and guarantee consistency with atomic transaction while denormalized for *analytical* system that focused on read-only queries

#### Expensive Joins
- Join can be expensive when we have 2 tables with large amount of rows, the materialized view discussed in [[2.1 Non Functional Requirements#Case Study Social Network Home Timeline]] is a form of denormalization
- However, we allow store the ID in the materialized view and we use application code to query the actual post with the ID
- This process is known as *hydrating* the ID
- This is to handle fast-changing data (e.g. social media posts which the like, comments change quickly)
- Hydration is still cheaper than the original large join due to *bounded ID lookup* and we can allow caching and parallelization more easily

#### Star and Snowflake: Schema for Analytics
Star Schema:
![[Pasted image 20261017135551.png]]
- Capture facts as individual events, which allow maximum flexibility of analysis
- The facts then hold reference to other tables known as *dimension tables*
- A variation of this template is *snowflake* where dimensions are further broken into subdimensions
- Snowflake are more normalized but more complex to work with

### When to use which Model
- Document model when
	- We need schema flexibility
		- Document model enforce *schema-on-read* which means the schema is enforced by application code, similar to *runtime (dynamic)* type checking
		- Relational database enforce *schema-on-write*, similar to static (compile-time) type checking
	- Application have document-like structure
	- Data Locality for read and write
		- If application needs access to entire document frequently
- Relational database
	- Better join support
	- Support M:M relationship
- Convergence of relational and document database
	- Recent relational databases added support for JSON and query operators
	- While some document databases added support for joins, secondary indexes and declarative query languages

## Graph Model
- Consists of nodes (vertices) and edges
- Handle complex many to many relationship
- Storing different types of data into 1 graph (*heterogenous* data)
- Allow graph algorithm like PageRank to operates
- Can be represented using
	- Adjacency List, each node represented by a list of nodes which they directly connected to
	- Adjacency Matrix, a cell represent whether the 2 nodes connect, the row and col represent the node

### Property Graph
- Nodes
	- A label identifying the type of the node
	- Incoming edge
	- Outgoing edge
	- A unique identifier
	- Key-value pairs describing properties
- Edges
	- A label identifying the type of the node
	- Node at the edge start
	- Node at the edge ends
	- A unique identifier
	- Key-value pairs describing properties
- Can store heterogeneous types of data
- Any nodes can connect to any nodes (no schema restriction)


#### Limitation: Binary Relationship
In a **traditional graph model**, an edge connects exactly **two vertices** (binary relationship). In contrast, a relational database can represent **N-ary relationships** (three or more entities) using a join table with multiple foreign keys.
- Example: Customer Purchases
A relational database can represent a three-way relationship with one row:

| Customer | Product | Store   |
| -------- | ------- | ------- |
| Alice    | Laptop  | Store A |

This guarantees that **Alice purchased a Laptop from Store A**.
In a graph, separate edges such as `Alice → Laptop`, `Alice → Store A`, and `Store A → Laptop` do not guarantee that these relationships belong to the same purchase event.
**Solutions**
1. Relationship as a Vertex (Reification)
Create an intermediate vertex representing the purchase event.
```
       Purchase #1
       /    |    \
    Alice Laptop Store A
```
- Preserves the association between all three entities.
- Supports additional properties such as date, quantity, and price.
- Commonly used in property graph databases.
2. Hypergraph
A **hypergraph** allows one hyperedge to connect multiple vertices simultaneously.
```
Hyperedge: Purchase(Alice, Laptop, Store A)
```
- Directly represents N-ary relationships.
- Less commonly supported by mainstream graph databases.
    

### Cypher
- A query language for property graph
```
CREATE 
(namerica :Location {name:'North America', type:'continent'}), 
(usa :Location {name:'United States', type:'country' }), 
(idaho :Location {name:'Idaho', type:'state' }),
(lucy : Person {name:'Lucy' }), 
(idaho) -[:WITHIN ]-> (usa) -[:WITHIN]-> (namerica), 
(lucy) -[:BORN_IN]-> (idaho)
```
- Query for a person that born in US and lives in Europe
```
MATCH 
(person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (:Location {name:'United States'}), 
(person) -[:LIVES_IN]-> () -[:WITHIN*0..]-> (:Location {name:'Europe'}) 
RETURN person.name
```
- The first query means find person has an outgoing `BORN_IN` edge to a vertex. From that vertex, you can follow a chain of outgoing `WITHIN` edges until eventually you reach a vertex of type `Location`, whose name property is equal to United States.
- The `:WITHIN*0..` means traverse through 0 or more `WITHIN` edges

### Graph Queries Using Recursive SQL
- A relational database can represent a **property graph** using two tables:
    - `vertices(vertex_id, label, properties)` — stores nodes and their properties.
    - `edges(tail_vertex, head_vertex, label)` — stores directed relationships.
- `tail_vertex` represents the source node, while `head_vertex` represents the destination node.
- Graph traversal can be implemented using **Recursive Common Table Expressions (CTEs)** with `WITH RECURSIVE`.
    
#### Recursive CTE
A recursive CTE repeatedly discovers new rows based on the results of the previous iteration until no new rows are found.
It consists of:
1. **Anchor query** — identifies the starting vertices.
2. **UNION** — combines results and removes duplicates, preventing repeated visits.
3. **Recursive query** — traverses edges to discover connected vertices.
Example: Find all locations within the United States.
```
WITH RECURSIVE in_usa(vertex_id) AS (
    -- Anchor: Find the United States location nodes
    SELECT vertex_id
    FROM vertices
    WHERE label = 'Location'
      AND properties->>'name' = 'United States'

    UNION

    -- Recursive: Find nodes that are have "within" edge pointing towards the location nodes within in_usa
    SELECT edges.tail_vertex
    FROM edges
    JOIN in_usa
      ON edges.head_vertex = in_usa.vertex_id
    WHERE edges.label = 'within'
)
SELECT * FROM in_usa;
```
**How recursion works:**
```
United States (1)       -- Anchor
    └── California (2)  -- Iteration 1
         └── SF (3)     -- Iteration 2
                        -- Iteration 3: No new rows, stop
```
- `JOIN in_usa` matches edges against vertices discovered in the previous iteration.
- `edges.head_vertex = in_usa.vertex_id` identifies edges pointing to known locations.
- `SELECT edges.tail_vertex` retrieves the connected source vertices.
- `WHERE edges.label = 'within'` restricts traversal to geographical containment relationships.
- `UNION` ensures each vertex appears only once in the accumulated result.
The complete queries
```
WITH RECURSIVE

-- 1. Find all locations within the USA
in_usa(vertex_id) AS (
    -- Anchor: Start from United States
    SELECT vertex_id
    FROM vertices
    WHERE label = 'Location'
      AND properties->>'name' = 'United States'

    UNION

    -- Recursive: Find locations within known USA locations
    SELECT edges.tail_vertex
    FROM edges
    JOIN in_usa
      ON edges.head_vertex = in_usa.vertex_id
    WHERE edges.label = 'within'
),

-- 2. Find all locations within Europe
in_europe(vertex_id) AS (
    -- Anchor: Start from Europe
    SELECT vertex_id
    FROM vertices
    WHERE label = 'Location'
      AND properties->>'name' = 'Europe'

    UNION

    -- Recursive: Find locations within known European locations
    SELECT edges.tail_vertex
    FROM edges
    JOIN in_europe
      ON edges.head_vertex = in_europe.vertex_id
    WHERE edges.label = 'within'
),

-- 3. Find people born in USA locations
born_in_usa(vertex_id) AS (
    SELECT edges.tail_vertex
    FROM edges
    JOIN in_usa
      ON edges.head_vertex = in_usa.vertex_id
    WHERE edges.label = 'born_in'
),

-- 4. Find people living in European locations
lives_in_europe(vertex_id) AS (
    SELECT edges.tail_vertex
    FROM edges
    JOIN in_europe
      ON edges.head_vertex = in_europe.vertex_id
    WHERE edges.label = 'lives_in'
)

-- 5. Find people satisfying both conditions
SELECT DISTINCT vertices.properties->>'name' AS person_name
FROM vertices
JOIN born_in_usa
  ON vertices.vertex_id = born_in_usa.vertex_id
JOIN lives_in_europe
  ON vertices.vertex_id = lives_in_europe.vertex_id;
```

### Triple Store and SPARQL
- Triple Store stores data in the format of `(subject, predicate, object)`
- Subject is a node
- Predicate is the type of the relationship
- Object can be either
	- A primitive type like string indicating a property of the subject
	- Or another node representing a relationship

#### SPARQL
- Works with RDF
```
SELECT ?personName WHERE 
{ 
?person :name ?personName. 
?person :bornIn / :within* / :name "United States". 
?person :livesIn / :within* / :name "Europe". 
}
```
- It does not differentiate between property or relationship
- Both are `predicate`
```
## Search for relationship and propery has different syntax
(person) -[:BORN_IN]-> () -[:WITHIN*0..]-> (location) # Cypher 
(usa {name:'United States'}) # Cypher

?person :bornIn / :within* ?location. # SPARQL
?usa :name "United States". # SPARQL
```

### DataLog
- Subset of Prolog
- Supported by some niche database
- Represent data using facts
- Based on relational data model not graph but allow powerful recursive queries
```
location(1, "North America", "continent"). 
location(2, "United States", "country"). 
location(3, "Idaho", "state"). 

within(2, 1).
within(3, 2). 
 
person(100, "Lucy"). 
born_in(100, 3). /* Lucy was born in Idaho */
```
- Define rules that construct virtual tables (like SQL view)
- This is a different way of thinking, breaking down things to rules just like we define functions in program
```
within_recursive(LocID, PlaceName) :- location(LocID, PlaceName, _). 
 /* Rule 1 - the anchor part */ 
 
 
within_recursive(LocID, PlaceName) :- within(LocID, ViaID), 
									within_recursive(ViaID, PlaceName). 
/* Rule 2 - recursive part */
 
migrated(PName, BornIn, LivingIn) :- person(PersonID, PName), /* Rule 3 */ 
									born_in(PersonID, BornID), 
									within_recursive(BornID, BornIn), 
									lives_in(PersonID, LivingID), 
									within_recursive(LivingID, LivingIn). 

us_to_europe(Person) :- migrated(Person, "United States", "Europe"). 
/* Rule 4 */ /* us_to_europe contains the row "Lucy". */
```

## Event Sourcing and CQRS
- Using different representation for writing and reading data can use the most optimized form for both
- The simplest, fastest form for data writing is event log, we append a self-contained JSON with timestamp, the log is *immutable*
- We then derive materialized views (also known as projections or read models) from the event logs
- The idea of using events as the source of truth and expressing every state change as an event is known as *event sourcing*
- The principle of maintaining separate read-optimized representation and deriving them from write-optimized representation is called *command query responsibility segregation*
- The request coming from the user called a *command*
- It is first validated, once validated in then executed and became facts, the event then logged
- The event log only consists valid event, the consumer *should not hold validation logic*
![[Pasted image 20261018111223.png]]
Pros
- Event is easier to communicate with the user for what happened
- Materialized views is reproduce-able, when it is bug, we can delete and recreate, it is also easy to create new view and run on existing event log
- Multiple views can be created to optimally handle different queries
- Reduce number of irreversible actions
- Serve as audit log
- Handle burst
Downsides
- When external source info is needed, should not incorporate when computing view, unless there is way to get historical data (e.g. get the exchange rate when the event occurred)
- Privacy concern - we might need to store personal info in different location with the event
- Reprocessing events can have side effects
- Order matters in processing events
