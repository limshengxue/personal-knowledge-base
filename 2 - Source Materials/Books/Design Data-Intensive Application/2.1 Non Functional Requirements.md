# 2.1 Non Functional Requirements
## Case Study: Social Network Home Timeline
### Reading Posts
We can have this query to get all the posts and users from the users we are following. We can use polling to get timely posts.
```SQL
SELECT posts.*, users.* FROM posts 
JOIN follows ON posts.sender_id = follows.followee_id 
JOIN users ON posts.sender_id = users.id
 WHERE follows.follower_id = current_user 
 ORDER BY posts.timestamp 
 DESC LIMIT 1000
```
But this is expensive, as a single user follows many users.
If we have 10 million user and we need poll every 5 seconds. It will be 2 million lookup. If each user follow 200 that we be 400 million lookups per second.


### Materializing 
- We can write to the follower timeline instead, at the rate of 5800 posts per second and per post reach 200, there will be only 1 million home timeline write.
- We can maintain a timeline cache for each user and enqueue the write
- When rate of posts spike, we accept it will temporarily take a bit longer for posts to show up
- The process of precomputing and updating the results of a query is called *materialization*
- The timeline cache is an example of *materialized view*
- Materialization speed up read but in return we have more writing load

#### Extreme Case
- Write cost of most users are acceptable since they have low amount of follower, but we need to consider celebrity account will millions of followers
- An example solution: store celebrity post elsewhere and have them merged into materialized timeline when it is read.

## Describing Performance
- Response Time:- the elapsed time from the moment a user make a request until they receive a response
- Throughput:- the number of requests per second or data volume per second that the system is processing
![[Pasted image 20261004095700.png]]
- When throughput pushed to close limit, it can enter a vicious cycle where it never recover - *metastable failure*
- For example, when long queue of requests cause client timeout and retry, this increases rate of requests even more, known as *retry storm*
- This can only recovered by reboot or reset
- There are some potential solutions
	- Increase and randomize the time of retries - *exponential backoff*
	- Stop sending requests to service that error or timed out -  by using *circuit breaker* or *token bucket*
	- Reject requests when close to overload - *load shedding*
	- Send response to ask client slow down - *back pressure*

### Latency and Response Time
- Response time is what client sees, include all delays incurred anywhere
- Service time - the duration which service is actively processing the request
- Queueing delay - when requests wait for processing
- Latency - a catchall term for time which request not actively process
![[Pasted image 20261004101116.png]]
- Queueing delays account for a large part of variability in response times. 
- It only takes a small number of slow requests to block the queue - *head-of-line blocking*

### Average, Median, Percentiles
- Mean response time is useful for estimating throughput but not useful to tell how many users experienced that delay
- Percentiles is usually better and used in SLO (service level objective) or SLA (service level agreement)
- High response-time percentiles known as *tail latencies* are important because this high load is usually important customer/customer who have most data
- In the other case, 1 UI action can send multiple requests to serve 1 end-user request. The end-user request will be blocked by the slowest request, known as *tail-latency amplification*
- p95 is often enough as p99 or p99.9 can affect by randomness and take very high cost to optimize
- Be aware that we should not aggregate percentile (e.g. percentile in several machines) by averaging


## Reliability and Fault Tolerance
- Reliability - "continuing to work correctly, even when things go wrong"
- Fault - particular part of the system stops working correctly
- Failure - the whole system stops providing the required service

### Fault Tolerance
- Continue providing required service despite fault occurring
- When the system cannot tolerate certain part become faulty, the part is called *single point of failure*
- Fault tolerance always have limit - (e.g. when all machine down)
- We can deliberately create fault to test a fault-tolerance system - *fault injection* / *chaos engineering*

### Hardware Faults
- A common method to tolerate hardware fault is add redundancy
	- RAID for disks
	- Servers with dual power and hot swappable CPU
	- Backup batteries for data center
- Redundancy is effective when component faults are independent
- Cloud provider focus less on reliability of a single machine while focus on service-level
- Cloud provider use availability zone to identify co-located resources

### Software Faults
- Often correlated, common for many nodes to run same software with the same bugs.
- Harder to anticipate, may only trigger under specific unusual conditions

### Human Errors
- Technical measure to help minimize include
	- Rollback mechanism
	- Gradual rollout of new code
	- Through testing
	- Well-design interface that encourage "right action" and discourage "wrong action"
	- Clear monitoring and observability tools for diagnosing production issues

## Scalability
- System ability to cope with increased load

### Load
- Often the measure of throughput (e.g. number of requests)
- Can narrow down to quantity that we care (e.g. number of simultaneously online users in social network)

### Shared-Memory
- Use a more powerful machine - *vertical scaling / scaling up*
- Parallelism on a single machine by using multiple processes or threads
- All threads share 1 RAM
- The problem is cost grows faster than linearly

### Shared-Disk
- Another approach is to use multiple machine with independent CPU and RAM but data on a shared array of disks connected using network-attached storage (NAS) or storage area network (SAN)
- Traditionally used for on-prem data warehousing
- But contention and overhead locking limit the scalability

### Shared-Nothing
- Shared-nothing also call *scaling-out* or *horizontal scaling* involves distributed system with multiple node
- Have potential to scale linearly
- Coordination between nodes is at software level 
- This provide greater flexibility and fault-tolerance


### Principles for Scalability
- Architecture of systems at large scale is usually highly specific to the application
- No *magic scaling sauce*
- Good general principle - break the system into smaller components that can operate largely independent from one another
- Another good principle is not to make things more complicated than necessary

## Maintainability
- Ongoing maintenance brings cost - fixing bugs, keeping system operational, investigating failures, adapting to new platforms, modifying it for new use cases, repaying technical debt, adding new features
- Legacy system can be hard to maintain
	- Outdated technologies
	- Institutional knowledge of how and why the system was designed lost when people left

### Operability
- Make it easy for organization to keep the system running smoothly
- Good operation can work around limitation of bad/incomplete software, but good software cannot run reliably with bad operations
- Automated operation bring benefit, but
	- Left the most complex problem for human
	- Hard to troubleshoot
- Data system can help operation by 
	- Allowing monitoring tools to check key metrics and give insight into system's runtime behavior
	- Avoid dependency on individual machines
	- Give good documentation
	- Give good default behavior
	- Self-healing
	- Predictable behavior

### Simplicity
- Software project mired in complexity - *big ball of mud*
- Complexity can cause budget and schedules overrun.
- Greater risk of introducing bug
- Hard to understand and reason
- Hidden assumption, unintended consequences, and unexpected interactions
- Essential complexity - inherent in the problem domain
- Accidental complexity - arises because of the limitations of our tooling
- However, boundaries between 2 can shift as tool evolves
- Abstraction can help manage complexity

### Evolvability
- New use case, business priorities change, new feature, platform change, regulatory requirement change
- The ease to modify data system and adapt it to changing requirement refer to as evolvability
