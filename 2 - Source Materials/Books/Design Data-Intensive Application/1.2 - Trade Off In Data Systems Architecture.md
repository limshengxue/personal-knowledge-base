# 1.2 - Trade Off In Data Systems Architecture
## Data Intensive
- Data-intensive application main challenge is data management
	- Storing and processing large data volumes
	- Managing changes to data
	- Ensuring consistency in face of failures and concurrency
- As opposed to compute-intensive which challenge is parallelizing very large computation

### Building blocks of data-intensive application
- Storing data for later retrieval (databases)
- Remember result of expensive operation to speed up read (cache)
- Allow users to search (index)
- Process event and data change as soon as they occur (stream processing)
- Periodically process a large amount of accumulated data (batch processing)

## Operational vs Analytical systems
- Operational - consists of backend service and data infrastructure where data is created. Read and modify data based on users' actions.
- Analytical - serve business analyst and data scientist. Read-only copy of the data and optimize for data processing
- Data engineer know how to integrate operational and analytical systems
- Analytics engineer model and transform the data to make it more useful for business analysts and data scientist

### Transaction Processing
- Transaction refers to a logical unit of a group of reads and writes
- Does not necessary involve money
- OLTP - online transaction processing, database built for modify data and query small number of records by a key (*point query*)
- OLTP runs query baked into application code. This prevents
	- Unauthorized access of data
	- Query that was not optimized by indexing
- OLAP - online analytical processing, scans over huge number of records and perform aggregation
- OLAP gives freedom for user to write query while there is user-facing app like Power BI that allow generate queries automatically

### Data Warehousing
- Company stop using OLTP database and use a separate database called *data warehouse* for analytics
- Why not running on OLTP directly
	- Data interest may spread and hard to combine dataset (problem known as *data silos*)
	- Schema and data layout for OLTP less suite analytics
	- Analytical queries can harm the performance of the operational system
	- Security and compliance reason, the analyst cannot access the data
- Data warehouse holds a read-only copy of the data
	- ETL: Data extracted from OLTP -> transformed into analysis-friendly schema -> clean and loaded into data warehouse 

### Date Lake
- Relational data model relies on SQL which is less suitable for 
	- Transforming data into vector/matrix for ML require custom code
	- NLP technique on textual data
	- CV technique for images
- Data lake simply contains files, without imposing particular file format, data model, or schema
- In some case, the data lake become intermediate stop of the data pipeline from OLTP to data warehouse

## Systems of Record and Derived Data
- Analytical system is usually derived data systems
- Operational system can combined both while derived data systems are caches or indexes that speed up read
- When we have derive data system, we need to sync data
- However, most databases are designed on the assumption that your application will always only need to use the single database, so data pipeline need additional effort

### Systems of Record
- Source of truth, holds authoritative version of the data
- User input is first written here

### Derived data systems
- Taking existing data from another system, transforming processing it in some way


## Cloud vs Self-Hosting

- Whether cloud is cheaper and easier than self-hosting depends on skills and workload of the system
	- Predictable load - better for self host
	- Available compute resources - better for self host
- Analytical systems often have extremely variable load
- Cloud comes with the limitations
	- Vendor controlled feature
	- Hard to diagnose as some internals info not accessible
	- Vendor lock in, vendor can increase price
	- Privacy and security concern

### Cloud Native System Architecture
- *Cloud native* - architecture that is designed to take advantage of cloud services
- Cloud instances can be provisioned faster and come in greater variety of sizes
- Leverage lower-level cloud services
	- Object storage services like S3, hide underlying physical machines, provide redundancy for backup

### Separation of storage and compute 
- In cloud, compute instances may have local disks attached, but cloud-native systems treat these disk ephemeral
- This is because this disk becomes inaccessible if the instance fails or when instance replace during scaling
- For persistence, use virtual disk storage like Amazon EBS, but this brings a problem: app become sensitive to network glitch because every I/O operation is a network call
- Cloud native system have the *separation of storage and compute* in mind
- It avoids using virtual disks and build on dedicated storage services such as S3 or cloud database
- Cloud native system also often be multi-tenancy: instead of separated machine for different customers, all customers use a shared set of hardware

### Operations in Cloud Era
- Due to cloud provider reduce administrative effort, bring to DevOps roles to combine develop and operations into a single team


## Distributed VS Single-Node System
- A system that involve several machines communicating via network is called distributed system
- Several reason to use this system
	- Inherent distribution - involve 2 or more interacting users, each using their own device
	- Requests between cloud services
	- Fault tolerance/ high availability - prevent failure when a single machine failed
	- Scalability - have huge load that need multiple machines to handle
	- Latency - have servers close to user 
	- Elasticity - can scale up/down based on demand
	- Specialized hardware - take advantage of different machine
	- Legal compliance
	- Sustainability

### Problems with Distributed Systems
- Every request and API call that traverses the network have possibility of failure
- Network call increase latency
- Hard to troubleshoot
- Hard to maintain data consistency

### Microservice
- Dividing a complex piece of software into multiple service
- Each service can update independently
- Each service runs on each own hardware
- However, it can breed complexity - complexity to test and deploy
- Can also be hard to evolve, as change in API easily propagate to all clients

### Serverless/ Function as a Service
- Management of infrastructure is outsourced to cloud vendor
- Vendor choose when to allocate/deallocate resources
- Pay only for the time the application code runs
- Suffer cold start
